# KoLab — Gloomy 加载机制移植：证据缺口与下一阶段验收（2026-11-12）

此清单根据同分支 `research/GLOOMY_LOADING_EVIDENCE.md` 制定；不代表独立加载后端已实现。

## 已证实的边界

- Gloomy 的 **KernelSU 引导** 和 **第三方 .ko 加载** 是独立路径。不能把 Native 的 KernelSU 专用镜像操作当成任何第三方模块的通用加载方法。（报告第 3–7 节）
- Java `Main.loadKo` 有已获 Root、设备厂商状态检查、暂存、摘要处理、模块加载尝试和额外 loader 尝试等环节。但存在步骤返回值未核验、内核结果未绑定具体模块字节的问题。（第 5 节）
- 外部 Kairos loader 的脚本内容不存在于当前证据中，不能确定它实际是否运行、是否影响了此前成功加载。（第 6 节）
- `DIRECT_WHITELIST_LOADED` 和内存中的 KAIROS 均不足以证明某个用户选择的模块由 Gloomy 本次新加载。（第 7、9 节）
- `hello.ko` 与本设备实际内核的 ABI/构建匹配须单独评估，Root 不是绕过内核模块签名与兼容检查的保证。

## 下一阶段优先调查（静态/只读）

1. **Loader 原件**：从原始备份寻找可信的 Kairos loader 正文与附属文件，并核验来源和哈希。仅静态检查；不运行 `.sh` 或未知 ELF。
2. **功能归因**：梳理历史上哪个界面操作对应哪个日志；收集可信的同次启动记录、操作前后模块快照和调用返回，而不是把不同日期的记录拼接成一条因果链。
3. **文件一致性**：确认被选择的模块字节和被加载内核观察对象之间能否建立关联；使用 SHA-256、内部模块名、vermagic、相关内核事件进行归因。
4. **设备限定**：只讨论已经取证的具体机型/内核构建；未验证范围返回不支持。
5. **KoLab 后端接口**：保留 `NOT_VERIFIED`、`ALREADY_PRESENT`、`LOAD_FAILED`、`LOADED_NEW`、`FUNCTIONAL_VERIFIED` 等明确状态，且不以普通 Root、调用成功、字符串输出替代内核接收证据。

## 开发约束

- 不复制原版 APK 包名/签名，不改动 Gloomy。
- 不实现自动关闭 SELinux、安全检测或签名保护的通用绕过，不执行未知二进制或脚本来“验证”猜测。
- 不默认卸载已加载模块，不盲目重试不同加载参数，不开无认证 Root 网络端口。
- 由用户在单独可恢复的测试条件下明确批准任何未来的真实模块操作；本阶段无动态尝试。
