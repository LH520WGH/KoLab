# KoLab — Gloomy 加载机制移植与跨应用共享：核心产品要求

**目标版本：KoLab 0.2+；状态：需求已确认，真实加载机制尚未成功移植。**
**本文件取代此前将 KoLab 定位为“纯静态文件管理器／纯审批中心”的方案。**

## 1. 用户定义的首要目标（不可换成文件仓库或模拟 API）

1. **复现 Gloomy 1.1 在用户的 Vivo V2408A 设备上已经实现的第三方 `.ko` 加载能力**，而不是仅实现 `insmod` 图形界面、Root 检测、兼容性预检、模拟 requestLoad。
2. 将这套真实加载能力封装为**独立、自己可维护的 KoLab APK + 必要的设备端加载组件**，以便不依赖 Gloomy 的 UI 或作者在线服务。
3. **提供常驻/按需服务模式**：KoLab 可以保有可复用的加载接口，其他用户允许的应用通过 KoLab 调用同一方法，而不是每个客户端重复集成原有工具。
4. **第三方客户端可能已经拥有 Root**；KoLab 的价值在于复用“厂商设备特定的模块加载方法”，不是替这些应用获得 Root，也不是给它们一个普通 Root Shell。
5. 用户明确不需要保留此前失败的导入记录；模块采用临时输入、特定操作后清理的工作流。
6. 优先降低内核崩溃和设备不可恢复风险；不默认卸载已加载的模块，不无条件重试不同参数，不未经确认开机重放加载操作。

## 2. 现有证据及尚缺证据

用户提供过 Gloomy APK 和多轮逆向结果。报告中确认：
- 应用包含 `Main.loadKo` 模块导入和加载路径；
- `exploit-vivo` 包含 `kw_plant_request`、`kw_insmod_allowlist`、`kw_bsp_write`、`kw_load_now` 等逆向分析线索；
- 存在 Vivo BSP 接口 `/sys/kernel/bsp_security/*`、`whitelist` 等相关分支，以及 `ksud late-load`、`su_daemon`；
- 同设备上曾成功加载第三方 `.ko`，但尚缺能把**成功加载具体归因到唯一函数分支**的完整运行证据；
- 曾发现硬编码的外部 Loader 路径，但当前该路径不存在，不能将其历史作用确认为零；
- 观察到当前 `insko_dfd_on=0`，但没有可信加载前基线，不能凭这一值单独归因。

**关键差距**：完整确定“哪一步使 Gloomy 能在该设备上加载原本不能通过常规方式载入的模块”；需要分离 Root 环境建立、厂商加载策略处理、最终内核加载调用、错误处理的真实职责。复制某一段 `insmod` 并不等于完成移植。

## 3. 要实现的最终系统形态

```text
[已有 Root 的 App A / App B]          [KoLab 管理界面]
           |                                |
           +---------- 本地 IPC/API --------+
                         |
                [KoLab 统一请求入口]
                         |
               [设备特定 Loader 后端]
               [Gloomy 功能的独立实现]
                         |
              [内核模块加载结果/错误]
```

- **产品主体是实际可工作的设备特定 Loader 后端**；前端 UI 与 IPC 是围绕该能力的使用入口，不是它的替代品。
- `KoLab UI`：用户手选 `.ko`，提交加载请求、查看结果、授权其他应用使用加载功能。
- `KoLab Bridge`：提供确定义的模块加载请求和状态反馈，申请方传入模块字节或受控文件句柄，不接收任意 Shell 命令。
- `设备后端`：与 Gloomy 已验证的实现进行函数级对照、等效性验证后实现；必须明确标注哪些属于授权的设备调试/实验功能，不能把未经确认的厂商安全限制处理逻辑包装成“任意驱动均可加载”。
- `服务生命周期`：界面退出后按需调用或保活，是否开机自启需单独实现并验证；**常驻接口**不等于**可在任意重启后继续使用相同内核权限/绕过状态**。

## 4. 功能验收顺序（优先级按用户目标）

### M0 — 找到 Gloomy 真正的有效加载支路
- 从 APK Java/Smali 和 `exploit-vivo` ELF 的函数级调用关系判断：入口、参数、实际调用分支、返回码及失败分支。
- 把 Gloomy 成功加载案例与日志对齐，不能仅凭字符串或当前模块列表声称已经成功归因。
- 梳理已验证的设备适配前提：机型、内核构建、模块 ABI、KernelSU 状态、BSP 接口状态、模块签名政策。
- 产出“已证实/合理推断/未知”对照表，给出最小可维护的替代实现设计。

### M1 — 设备加载后端
- 分离模块文件预检、特权检查、设备兼容性检查、加载请求与结果反馈。
- 在合法授权设备与内核允许的操作范围内实现 Loader；未获得完整证据前，**不可宣称 Gloomy 关键能力移植成功**。
- 不执行任意导入 `.sh` 或自解压程序。
- 不自动卸载正在运行的模块；不能以一次加载失败为由修改全局安全策略或连续尝试多个高风险方案。

### M2 — 共享服务及客户端调用
- 提供可供其他 App（包括已有 Root 的 App）调用的显式 IPC 接口。
- 可由用户授权受信任客户端，也可在设备仅限用户自用的环境中配置简化流程；这部分是**分发加载能力的入口，不是加载原理**。
- 不对外开放无认证 Root TCP 服务；明确请求来源、模块和返回码。
- 限定调用类型为指定文件的模块加载，不提供任意命令执行或任意 /data/adb 写入服务。

### M3 — 常驻和自主管理
- 支持服务就绪状态、启动/停止、客户端授权撤销、异常后状态恢复。
- 常驻仅保证服务存在，并不保证重启后内核模块与厂商安全状态保持；有 Root/设备内核兼容需求。
- 分离 Android APK 生命周期、Root 后端进程生命周期、内核加载状态三个层次。

## 5. 不能跳过的事实

- 即使第三方应用已经 Root，也不代表其 `insmod` 自动通过 Vivo 的设备特定检查。
- 目前 KoLab 0.1.0 **不具备 Gloomy 这种真实的设备特定加载能力**。M0/M1 未完成前，不把 UI、Binder、模拟响应宣称为“移植成功”。
- 作者是否能远程禁用与内核是否接受模块是两个独立问题。原 APK 不依赖云端验证并不能保证未来系统升级后还能加载。
- 模块初始化代码即使成功通过载入检查仍可导致 Kernel Panic，因此不存在对任意 `.ko` 的零重启保证。

## 6. 用户已定偏好

- 不需要保存原先失败的导入记录
- 保留原版 Gloomy 作对照，不直接改动手机内核或现有 Root 环境
- 核心目标优先级为“真实方法移植 > 常驻可调用 > 客户端授权/界面美化 > 文件管理”
- 后续真正可用的 APK 应以**实际设备上调用成功的证据**验收，不能仅凭 Actions 构建成功验收
