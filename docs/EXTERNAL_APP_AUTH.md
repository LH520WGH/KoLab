# KoLab Bridge — 修订需求与系统边界

**状态：架构方案，非已实现/可加载 APK。**

## 用户的真正目标
不再把 KoLab 定位为“个人 .ko 文件仓库”，改为类似 Shizuku 的本地服务入口：

- 已获得 KernelSU/Root 的用户选择信任的 Android 应用；
- 可信应用通过稳定的进程间接口，请求 KoLab 协调已授权、且与设备兼容的内核模块操作；
- KoLab 提供统一授权、静态预检、状态回报；
- 尽量不保存用户导入文件历史，也不保留失败的驱动记录；
- 不依赖原版 Gloomy APK 或作者的在线服务；
- 在合法的系统加载政策范围内工作；不能声称通用 API 可以突破 Vivo 或内核模块签名策略。

## 澄清：Root、Binder 与内核模块许可是不同边界

- **Root** 允许执行受 Linux DAC/SELinux 约束的高权限操作，但不必然使任意 .ko 可加载。
- **Shizuku 式 Binder 服务**只负责跨应用调用与授权，不提供新的内核加载能力。
- **内核层**最终决定 init_module/finit_module 是否接受模块；具体签名、KMI、版本、页面大小等条件仍必须满足。
- 任何已有授权的加载实现仍受版本、合法性和来源限制；不要复用未经审查的 exploiter 二进制、破解签名检查或全局关闭厂商安全策略。

## 目标架构

```
[App A / App B（用户明确允许的客户端）]
      | Binder IPC (caller UID + signing certificate)
[KoLab Bridge（授权管理界面 + API + 预检）]
      | 仅处理经认证、经批准的明确操作
[受限的系统适配器 / 现有用户授权的特权环境]
      | 设备内核接受的正规模块加载接口
[Android / Vivo Kernel]
```

## API（最小功能集）

- getCapabilities(): 返回设备、内核、服务是否就绪，以及“是否支持受控加载”（可为 false）；
- inspectModule(uri): 读取已授予访问权的 content URI，将文件临时复制到私有位置作 ELF/modinfo/摘要检查；不运行文件；
- requestLoad(uri, moduleSha256): 校验调用方、身份、模块哈希、设备兼容性，创建“加载请求”；**不会自动突破内核安全策略**；
- getRequestStatus(requestId): 返回请求状态（待批准 / 不支持 / 拒绝 / 成功 / 失败）；
- revokeClient(packageName): 仅允许用户在管理界面撤销授权。
- 不提供 exec(command)、任意路径写入或 runShellScript API；不暴露无认证 TCP 端口。

## 权限

- 其他 App 已有 Root **不等于自动得到 KoLab 服务许可**；
- 对每次 Binder 交易读取真实 Binder.getCallingUid()，结合 getPackagesForUid()、签名证书及授权列表验证；
- 拒绝伪造包名、含糊来源、签名变化、无法映射的共享 UID；
- 按 App / 模块 SHA-256 / 操作范围授权；默认只读，敏感操作每次确认；
- 申请授权由用户在 KoLab 界面主动操作；运行时不自动批准；
- Root App 从系统安全视角已经拥有很高权力；此授权中心主要防误用/规范 API，而不是可防御任意恶意 Root App 的硬安全边界。

## 用户体验

- 主屏：KoLab Bridge 服务状态、内核版本、受控加载支持状态；
- 可信应用：用户选择授权哪些 App，查看真实包名与签名证书，随时撤销；
- 操作请求：查看具体申请、文件名、模块元信息、请求原因、批准或拒绝；
- 导入文件只是为某次请求暂存，不建立永久历史仓库；在请求结束/失败后清理临时副本（异常崩溃时下次启动清理）；
- 普通 .sh 和自解压脚本**不是内核模块**，不运行；可以提示其文件类型与危害；
- 无长期驱动导入记录（除非用户以后明确改变需求）；授权列表可保存，操作日志只暂存必要诊断信息。

## 开发分阶段验收

1. **Bridge 原型 APK**：安装、界面、已授权客户端列表、Binder caller 身份确认、模拟 requestLoad 返回“不支持/待批准”，测试拒绝未授权客户端。
2. **模块兼容性预检**：只读 .ko 解析、标记签名/KMI/设备版本约束、异常文件/归档分类；无 Root 写入。
3. **可维护的合规执行适配层**：仅在确认实际设备有可用、授权且不违反内核安全策略的加载通路时，连接受控执行器；真实调用必须逐次由用户批准；不运行外部不明脚本或复用闭源漏洞利用。
4. **真机安全验证**：先在测试模块、可恢复设备条件下验证拒绝路径、错误码、客户端鉴权，成功与否由设备侧运行日志确认。

## 非目标与限制

- 不复制 Shizuku 的通用命令执行权；
- 不向其他 App 分发 Root，也不提供通用的 Vivo 安全限制绕过；
- 不保证任意 .ko 加载成功，更不能保证绝对不 Kernel Panic；
- 不能因为原版 Gloomy 曾经成功就认定新应用具备相同能力。
