# Gloomy / Vivo 6.6.127 机制核对 — 第三方描述与现有证据

## 来源边界
本页核对用户引用的酷安作者说明与 DSH Go 提供的 `research/GLOOMY_LOADING_EVIDENCE.md`（2026-11-11）。
作者描述是**外部经验报告**，不是本机独立验证结果。没有读取或运行 own127、load_kairos.sh 或外部 Kairos loader。

## 确实相符的地方
- Gloomy 的用户驱动路径要求已有 Root，并检查设备特定门值。
- Java 控制流包含以模块 SHA-256 派生的8字节摘要数据处理、厂商节点交互、普通模块加载尝试。
- “SHA-256 前8字节”是64 bit（二进制8字节），**不是前8个十六进制字符（只有4字节）**，也不是32字节完整摘要；文字表述中“前8位”会造成歧义。
- Android Binder / IPC 授权只能提供服务分发，并不等于已经验证设备加载后端。

## 尚无证据认定的部分
- 作者声称 own127 执行后厂商门被打开、保护入口不再拒绝，但这份报告没有同一次启动从准备到新模块生效的完整时序。
- 特定模块的加载成功是否由 Java 直接加载、额外 Kairos loader 或先前状态共同造成，缺少同次加载日志证明。
- 文件哈希与正在加载的字节是否完全一致、命令退出状态与内核接收事件是否一一对应。
- 成功是否可在系统升级、开机后的其他设备状态复现。
- 改变厂商安全设置的影响范围、恢复条件、SELinux 策略影响尚不明。

## KoLab 当前工程决定
1. 保留用户已经测试成功的 Binder 跨应用查询及静态文件检查。
2. 添加**只读设备诊断**：显示厂家门值是否可读、内核版本、page size、SELinux 状态与模块相关系统状态；权限不足时显示不可读取，而非默认门已开。
3. 导入时只进行 ELF/modinfo 预检和摘要计算，不保留文件，也不执行脚本。
4. 后端 `NOT_VERIFIED` 状态由程序直接返回；不显示虚假的“已移植”“可刷入”。
5. 本阶段不集成 own127、厂商防护修改、任意模块执行或可被其他应用滥用的 Root 执行接口。

## 下一步验收资料
需要能确认**同一次**用户操作里，精确模块字节、设备状态、调用返回、内核新增加载事件与模块功能相互对应的证据。具体加载机制必须在合法的测试环境中验证，不能仅据一篇经验帖作通用许可结论。
